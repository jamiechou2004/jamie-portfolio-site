THE CHALLENGE

The analysis was ready.
The decision wasn’t.

An image analysis can describe a concern without making the next step clear. In Skin Care, the design question was how to move from reading a result to deciding what to do with it.

The team’s goal was to give people a reason to continue using Chance. I translated that goal into three connected design questions.

Continued use is a goal to validate, not a measured outcome of this case.

BASIS FOR THE DESIGN

The original result screen and its redesign show the change in information order. The questions below are design interpretations of that interface problem; they are not presented as measured research findings.

PRODUCT ARCHITECTURE

Understand → decide → keep caring.

Functional value

Use uploaded visual context and skin feedback to organize visible redness, congestion, and texture concerns. The goal is to help someone identify what needs attention.

Decision value

Turn abstract analysis into a readable priority and care direction, with explanations before optional product support.

Continuing value · hypothesis

Translate one insight into a daily plan, completion records, and future adjustment. Continued care and repeat use are design goals to validate.

The intended progression is from having advice to having a plan that can be followed and recorded. It is not evidence of improved skin health or retention.

DECISION 01 / STRUCTURE THE RESPONSE

Organize the answer around
the person’s next decision.

I moved from parallel content categories to a sequence of user questions: understand the state, find the priority, then choose an action.

Basis

The original prototype and redesigned result below provide the interface comparison.

Choice

Put the current state, priority, and action before optional product support.

Trade-off

The sequence prioritizes a next step over equal visibility for every content category. Its effect on understanding still needs testing.

THE ACTUAL BEFORE & AFTER

Change the order, not just the styling.

The earlier layout lacked a clear action, sufficient explanation, and continuing status feedback. The new sequence answers five questions: current state, explanation, priority, today’s action, and optional support.

01

Start with a priority

The summary brings the overall state, top focus, and primary action together.

02

Explain the observations

Skin Snapshot and Skin Pattern give the analysis a readable structure. Separating visible observations from AI inference remains an important content check.

03

Make the next action concrete

The routine turns advice into ordered steps. Its completion controls communicate an intended action, not evidence of sustained use.

04

Keep product support optional

Recommendations follow the explanation and routine, so shopping does not lead the experience.

DESIGN REASONING

Priority before completeness.
Action before shopping.

The information order should help a person make a choice. More generated detail is useful only when they can understand what to do with it.

A clearer answer creates a new question: how can someone go deeper without starting over?

DECISION 02 / ENABLE CONTEXTUAL FOLLOW-UP

The next question starts
with the answer they have.

I connected follow-up to the current analysis, with suggested questions for people who need a starting point and free input for those who already know what they want to ask.

Basis

The documented reference study explores a shared composer and answer-linked suggestions.

Choice

Suggested questions, free text, and optional images all extend the current analysis.

Trade-off

Suggestions offer a start while editable input preserves individual intent. These are complementary paths, not an A/B-tested winner.

DESIGN DECISION

Two entry points, one context.

Choose a suggested question or type your own. Optional images can add detail to the question in the same composer. Both paths extend the current analysis.

TWO WAYS TO START

Choose a suggestion, or ask in your own words.

Both start in the same composer. A suggested question fills the input for review and editing; users can also type their own question directly. Selecting a suggestion does not send it.

DESIGN REASONING

Two entry points.
One continuing conversation.

Suggestions help someone get started; direct typing lets them express a question in their own words. Both can be reviewed before sending and carry the existing analysis into the follow-up.

The material shows the interaction path. Whether suggestions help people ask a useful question still needs validation.

DECISION 03 / MAKE INPUT AND RECOVERY EXPLICIT

Keep the request visible.
Make interruptions understandable.

Input, waiting, and failure belong to the same journey. Reviewing attachments before sending keeps the request deliberate; specific feedback shows which step needs attention.

Basis

The supplied screens show selection counts, upload feedback, invalid input, and a retake entry.

Choice

Expose boundaries during selection and distinguish waiting from failure.

Trade-off

Additional images add processing constraints. The ten-image cap is a current design boundary, not a demonstrated optimum.

COMPLETE INPUT FLOW

Enter, select, preview, adjust.

Start from the existing result. Open the composer or image entry, take a photo or choose from the library, then select and review attachments. Remove an image or add more before sending text and images together.

DESIGN REASONING

Context carries forward.
Sending stays deliberate.

Previewing attachments makes the contents of the next request visible. The user can adjust the message before asking the system to respond.

03 / LIMITS & STATES

Make the boundary visible.
Make the state specific.

Adding more images also adds constraints. I worked through the selection limit and upload feedback so people can see what is allowed and which step needs attention.

INTERACTION DETAIL

Show the rule while selecting.

The picker displays the selected count. At ten images, further selection is unavailable.

DESIGN REASONING

Feedback before submission.

The limit appears where people choose images, rather than after they have finished composing. Ten is the current design limit; its suitability still needs technical and usability validation.

INTERACTION DETAIL

Waiting and failure need different feedback.

Show the status on the relevant attachment. If someone sends before an upload completes, explain that they need to wait.

DESIGN REASONING

Locate the problem.

A specific state helps people distinguish a pending image from a failed one. Preserving context and retrying only the failed step remain proposed recovery work.

Recovery boundary

The supplied generation-failure UI shows a retake entry. It does not yet demonstrate a complete context-preserving retry flow. Optional notifications also depend on permission and delivery behavior that still need validation.

AI STATES & RECOVERY

Explain the interruption.
Show a way forward.

Invalid input, long processing, and generation failure are different situations. Each needs an explanation and a next step.

01 / INVALID INPUT

Translate a technical error into a useful instruction.

The earlier message exposed a system variable. The revision names the required image, explains the mismatch, and offers a retake entry.

DESIGN REASONING

“Please use a skin photo” is actionable when paired with why the current image cannot be used. A technical identifier does not help someone correct the input.

Change: replace the exposed technical identifier with the required photo type and a retake action. Basis: the supplied before/after screens. Limit: the screens demonstrate the wording change, not a measured recovery success rate.

02 / LONG PROCESSING

Waiting should not require staying.

The design offers an optional notification entry so people can choose to leave while processing continues.

DESIGN REASONING

Communicate that processing is ongoing while leaving the choice with the user. Notification permission, actual delivery, and whether this reduces waiting burden remain to be validated.

03 / GENERATION FAILURE

Move from starting over to continuing.

The supplied interface currently offers “Snap Again” after failed recognition.

PROPOSED NEXT ITERATION

Preserve the question and images, then retry the failed step. This recovery flow is a design direction, not functionality demonstrated by the current screen.

  1. Explain what happened
  2. Explain why
  3. Offer the next action
